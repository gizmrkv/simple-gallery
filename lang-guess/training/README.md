# lang-guess training pipeline

`lang-guess`(文字ベース言語識別のONNXモデル)をゼロから学習するための、
オフラインPyTorchパイプライン。ここで作るのはブラウザ側(`../src/`)が
読み込む `../public/model/lang-id.onnx` と `../public/model/vocab.json` のみで、
フロントエンドのコード自体はこのディレクトリの外(`../src/`, `../index.html`
など)にあり、別途管理されている。

対象は31クラス(ラテン文字表記27言語 + ローマ字化した日本語/中国語/韓国語 +
「どの言語でもない」unkクラス)。データソース・ライセンス・ローマ字化の
簡略化ルールは [DATA.md](DATA.md) を参照。

## セットアップ

```bash
cd training
uv sync
```

## 再現手順

1. データ収集(ダウンロード+パース+ローマ字化。生データは`data/raw/`に
   キャッシュされ、初回のみネットワークアクセスが発生する):

   ```bash
   uv run python prepare_data.py
   ```

   `data/words.csv`(word,lang)と`data/data_summary.json`(言語別件数)が
   生成される。

2. UNKNOWNクラス(合成ネガティブ)を追加:

   ```bash
   uv run python generate_unknown.py
   ```

   `data/words.csv`に`unk`ラベルの行が追記される(再実行しても重複しない)。

3. 学習。まずdebugモードでパイプライン全体の疎通を確認してから、
   本番設定でフル学習する:

   ```bash
   uv run python train.py --config 0000 --debug   # 縮小データで1-2エポックのスモークテスト
   uv run python train.py --config 0000           # フル学習
   ```

   `configs/0000.yml`にハイパーパラメータがある。結果は
   `results/0000/`(debug時は`results/0000_debug/`)に
   `best_model.pt`(ベストチェックポイント)・`metrics.json`・`output.log`・
   使用したconfigのコピーとして出力される。

4. ONNXへのエクスポート(+検証):

   ```bash
   uv run python export_onnx.py --config 0000
   ```

   `../public/model/lang-id.onnx` と `../public/model/vocab.json` を書き出し、
   onnxruntimeで実際に推論して、エクスポート前のPyTorchモデルの出力
   (argmax・確率とも)と一致するかを自動検証する。不一致があれば
   非ゼロ終了コードで失敗する。

## ディレクトリ構成

```
training/
  constants.py       # ラベル順序・文字語彙(フロントエンドの契約と一致させる定数)
  romanize.py         # 日本語(ヘボン式簡略)/韓国語(RR簡略)/中国語(拼音正規化)の変換ロジック
  prepare_data.py     # 生データのダウンロード・パース・ローマ字化 -> data/words.csv
  generate_unknown.py # unkクラス(合成ネガティブ)の生成 -> data/words.csvに追記
  dataset.py          # トークナイザ・PyTorch Dataset・層化train/val/test分割
  model.py            # 文字CNN(CharCNN)
  train.py            # 学習ループ(dataclass Config + tyro + structlog)
  export_onnx.py       # ONNXエクスポート + vocab.json書き出し + 検証
  configs/0000.yml    # ハイパーパラメータ設定例(v1、31クラス)
  configs/0001.yml    # v2設定(23クラス、epochs/num_filtersを増やした版)
  configs/0002.yml    # v3設定(0001と同一。複数言語重複単語のソフトラベル化)
  data/               # 生成物(.gitignore対象。生データ・データセットCSV)
  results/            # 学習結果(.gitignore対象。チェックポイント・ログ・metrics.json)
```

## 学習結果

### v1 (configs/0000.yml, 31クラス, 2026-09-06実行)

- データ件数: 全体1,533,912件(train 1,227,160 / val 153,376 / test 153,376)。
- テスト全体精度: 50.96%(31クラス分類のランダム基準は約3.2%)。
- 言語別精度が高い例: 中国語(ピンイン)87.6%、日本語(ローマ字)85.7%、
  韓国語(ローマ字)85.5%、フィンランド語64.3%、バスク語63.0%。
- 言語別精度が低い例: デンマーク語13.9%、チェコ語15.7%、インドネシア語17.2%、
  ベトナム語22.1%、スウェーデン語22.0%。
- unkクラス: precision 0.948 / recall 0.601。

読み取り専用の混同行列分析の結果、精度低下の主因は(a)近縁言語ペア/トリオでの
双方向の混同(id⇔ms, cs⇔sk, sl⇔hr, sv⇔no⇔da, es⇔pt, lt⇔lv)と、
(b)ベトナム語(vi)がアクセント記号除去により極端に短く曖昧な文字列になり、
ほぼ全言語で誤答が一方的にviへ吸着する現象、の2つだと判明した(詳細は
[DATA.md](DATA.md)の「クラス統合/ベトナム語除外」節参照)。

### v2 (configs/0001.yml, 23クラス, 2026-09-06実行)

上記の知見を受けて6クラスタを統合・ベトナム語を除外(`constants.py`の
`LABEL_MERGE_MAP`/`DROPPED_LANGS`)、かつ`epochs`を10→25、`num_filters`を
64→96に増やして再学習した。

- テスト全体精度: **59.71%**(v1比 +8.75pt、23クラス分類のランダム基準は約4.3%)。
- 統合したクラスタの精度: `lt_lv` 59.2%、`sl_hr` 51.3%、`es_pt` 44.4%、
  `id_ms` 41.1%、`scand` 38.3%、`cs_sk` 36.3%(いずれも統合前の該当言語の
  最低値より大幅に改善。例: id 17.2%→id_ms 41.1%、da 13.9%→scand 38.3%)。
- ローマ字化言語は引き続き高精度: 中国語(ピンイン)91.6%、韓国語(ローマ字)
  88.3%、日本語(ローマ字)87.4%。
- unkクラス: precision 0.944 / recall 0.671(v1比recallが+7pt改善。
  ベトナム語除外で「誤って何らかの言語と判定されてしまう」割合が減った)。
- ONNXエクスポート後の検証: PyTorch出力との差はsoftmax確率で最大2.38e-07
  (12サンプルすべてargmax一致)。モデルサイズ326.5 KiB。

再度の混同行列分析では、以前ほど極端な単一の吸着先はなくなったものの、
`en`(英語)と`fr`(フランス語)が他の多くの言語(特にゲルマン・ロマンス系や
統合後のクラスタ)の誤答先として比較的よく出てくる傾向が残っている
(例: `scand`の誤答の上位が`fr`・`en`、`id_ms`の誤答上位が`en`)。これはvi問題
のような一方的な吸着ではなく、英仏が語彙的に他言語と重なりやすい・
学習データ量が多い、という性質による緩やかな偏りで、cs/sk等のような
明確な「ほぼ同一言語」のペアではないため、今回は追加の統合は行っていない。

このように単語単体からの言語推定は本質的に難しく(特に近縁言語間)、
精度に上限がある点はデモの前提として許容している。フロントエンド側は
単一の断定ではなく確率ランキング形式で表示するため、上位に正解が
含まれていれば体験として成立する設計にしている。

### v3 (configs/0002.yml, 23クラス+ソフトラベル, 2026-09-06実行)

v2までは、複数言語に同じ綴りで重複登場する単語(全体の12.47%)が矛盾する
ハードラベルとして学習され、実質ノイズになっていた点を修正した
(詳細は[DATA.md](DATA.md)の「複数言語にまたがる単語のソフトラベル化」節
参照)。ハイパーパラメータはv2から変更していない。

- データ件数: 重複単語の集約により、一意な学習example数が94.6万件
  (train 907,822 / val 113,465 / test 113,465。v2の133.5万行から約29%減)。
- テスト全体精度: v2と同じ基準(予測クラスが単語の代表ラベルと完全一致)で
  再計算すると**73.27%**(v2比 +13.56pt)。「予測クラスが、その単語に
  有効な言語のいずれかと一致」という、複数言語にまたがる単語により忠実な
  基準では**75.80%**(`results/0002/metrics.json`に記録されている数値)。
  テストセットのうち複数言語にまたがる単語は6.4%で、いずれの基準でも
  改善は重複単語の扱いを直しただけでは説明しきれない大きさがあり、
  矛盾ラベルの除去が単一言語の単語の学習にも良い影響を与えたことを示唆する。
- 具体例(`mission`: 統合後13クラスに有効): v2ではフランス語27%のみが
  突出していたが、v3ではフランス語25.5%・英語25.2%とほぼ拮抗するように
  なり、上位6言語がすべて実際に有効な言語と一致した。`monster`
  (英語含む13クラスに有効)も、v2では上位が北欧語9.1%・英語8.3%と
  ほぼフラットだったのに対し、v3では英語21.7%が明確に最上位になった。
- unkクラス: precision 0.959 / recall 0.653(v2の0.944/0.671とほぼ同水準。
  クラス重みの計算方法変更にもかかわらず退化していないことを確認)。
- ローマ字化言語は引き続き高精度: 韓国語(ローマ字)93.5%、中国語
  (ピンイン)92.9%、日本語(ローマ字)88.2%(いずれも上記「有効な言語との
  一致」基準)。

## 備考

- `data/raw/`・`data/words.csv`・`results/`・`.venv/` は`training/.gitignore`
  で除外している(生データ・データセットCSV・チェックポイントは
  スクリプトから再生成できるため、リポジトリにはコミットしない想定)。
- `train.py`はCUDAが実際に使えるか(演算を1回試して)確認し、使えれば
  GPUを、ダメならCPUを使う(`torch.cuda.is_available()`だけでは不十分:
  このマシンのGPU(GTX 1080, CC 6.1/Pascal)は当初インストールされていた
  torchビルド(cu130)ではis_available()がTrueを返すのに実際の演算は
  「no kernel image is available」で失敗した。`pyproject.toml`で
  `~/ml-experiments`と同じ`pytorch-cu126`インデックスを明示的に指定する
  ことで解決した)。ただしこのモデルは非常に小さい(パラメータ約8万個)ため、
  GPU使用によるエポックあたりの所要時間短縮はほぼ確認できなかった
  (CPU/GPUともに1エポック約60〜65秒)。
